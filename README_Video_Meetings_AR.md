# «إنجاز» — الاجتماعات المرئية داخل المنصة

**حالة النسخة:** تحديث أولي للتجربة على بيئة مستقلة؛ غير معتمد للنشر المباشر على الإنتاج أو لمعالجة اجتماعات مؤسسية حساسة قبل استكمال قائمة الفحص الأمني.

## 1. النطاق المعتمد
- يحتفظ بالنموذج التنظيمي الأصلي: مدير عام الإدارة العامة للقروض المتعثرة، المستشار المستقل، رؤساء الأقسام والموظفون؛ **لا يتضمن** الهيكل المؤسسي متعدد القطاعات الملغى.
- يضيف صفحة «الاجتماعات المرئية» داخل إنجاز (واجهة عربية RTL)، دون التأثير في شاشات المهام والتكليفات والبريد والمحادثات.
- المواعيد والضيوف والمحاضر تحفظ في PostgreSQL الحالية في جداول جديدة فقط: `video_meetings`, `video_meeting_invitations`.
- الفيديو والصوت ومشاركة الشاشة تنتقل بين المستخدمين وخدمة LiveKit عبر WebRTC، وليس إلى PostgreSQL أو إلى خادم FastAPI.

## 2. الوظائف المضافة
- إنشاء اجتماع مجدول لمدة 15–180 دقيقة وبحد أقصى 16 شخصًا بما فيهم المنظم.
- دعوة أشخاص بعينهم؛ الموظف ورئيس القسم يرسلان الدعوات داخل نطاق قسمهما أو للإدارة العليا فقط؛ المدير العام والمستشار يمكنهما دعوة الموظفين من القسمين.
- ربط اختياري بمهمة؛ في هذه الحالة يقتصر المشاركون على منشئ المهمة والمكلف بها، ولا يُسمح باطلاع أشخاص آخرين.
- عرض قائمة الاجتماعات الخاصة بكل مستخدم، وإشعار عددي بالدعوات غير المقروءة.
- إنشاء محضر نصي للقرارات والتوصيات؛ يُعدله منظم الاجتماع فقط ويقرأه المدعوون.
- غرفة داخل الواجهة مع أزرار الميكروفون والكاميرا ومشاركة الشاشة؛ **لا يوجد تسجيل آلي للصوت أو الفيديو**.
- لا يستطيع المدير العام فتح اجتماع لا يُدعى إليه، حتى لو كان أعلى درجة تنظيمية.

## 3. صلاحيات الانضمام وأمان الرموز
- كل طلب خادم يتطلب جلسة إنجاز سارية وCSRF.
- يتحقق الخادم من دعوتك ثم يسمح بتوليد رمز LiveKit JWT موقع بمفتاح محفوظ بالخادم فقط.
- رمز الاجتماع مدته **5 دقائق** للدخول، ومقيد بغرفة محددة وهوية محددة؛ لا يكشف مفتاح LiveKit السري.
- يُسمح بالدخول بدءًا من 15 دقيقة قبل موعد الاجتماع وحتى موعد نهايته + 15 دقيقة، ولا يتم قبول المواعيد المنتهية أو الاجتماعات التي أوقف منظمها إصدار تصاريح جديدة.
- تعطيل حساب المستخدم يمنعه من استصدار أي رمز جديد.
- *حدّ النسخة الأولية:* إن خرج المستخدم من إنجاز أو أنهى المنظم الاجتماع، فإن ذلك **لا يضمن فصل المشاركين المتصلين فعليًا بغرفة LiveKit**؛ يجب تنفيذ آلية إغلاق الغرفة عبر LiveKit Admin API ومراقبة صلاحية الجلسات قبل الإنتاج. كما لا يضمن رمز الـ5 دقائق إبطال اتصال قائم.

## 4. متطلبات التكامل — Railway
أضف المتغيرات التالية إلى **بيئة تجريبية مستقلة** وليس إلى إنتاج إنجاز في هذه المرحلة:

```env
LIVEKIT_URL=wss://YOUR-APP.livekit.cloud
LIVEKIT_API_KEY=YOUR_KEY
LIVEKIT_API_SECRET=YOUR_SECRET
MEETINGS_VIDEO_APPROVED=false
MEETINGS_ALLOW_CDN_SDK=false
```

- `LIVEKIT_URL`: عنوان WSS الخاص بمشروع LiveKit المعتمد من الجهة (Cloud أو خادم خاص مؤمّن).
- `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET`: يُدخلان في Railway Variables، ولا يوضعان في GitHub أو app.js أو أي لقطة شاشة.
- `MEETINGS_VIDEO_APPROVED`: **false افتراضيًا**؛ لن تعمل الاتصالات المرئية إلا عندما تضبط true بعد الموافقة.
- `MEETINGS_ALLOW_CDN_SDK`: **false افتراضيًا**؛ للحماية يُفضّل استضافة نسخة ثابتة ومراجعة من `livekit-client` على نفس نطاق إنجاز تحت `/assets/livekit-client.umd.min.js`. تتطلب هذه الطريقة تعديل عملية نسخ ملفات Docker حسب بنية المستودع، وتثبيت نسخة موثّقة من الحزمة بعد فحصها وإجازتها من أمن المعلومات.
- لأغراض **اختبار غير حساس فقط**، يمكن ضبط `MEETINGS_ALLOW_CDN_SDK=true` بعد اعتماد هذا الاتصال؛ عندئذ تُحمّل مكتبة JavaScript المثبتة للإصدار `2.25.0` من jsDelivr ويُضاف هذا المصدر إلى CSP. **لا يوصى بتفعيل هذا الخيار في الإنتاج المؤسسي**. قد يحجب ADF Security اتصال CDN كما حجب طلب الدخول سابقًا.
- لا توجد مكتبات Python جديدة مطلوبة في هذا التحديث؛ يتم توقيع رموز JWT باستخدام `hmac/hashlib` المدمجة.
- في حال عدم اكتمال الإعدادات، تسمح المنصة بجدولة الاجتماعات والدعوات والمحاضر فقط، وتظهر رسالة واضحة بأن الفيديو غير مفعل.

## 5. النشر التجريبي
1. خذ نسخة احتياطية من قاعدة بيانات PostgreSQL الإنتاج (واختبر الاستعادة)، ثم أنشئ بيئة **staging** بقاعدة منفصلة.
2. فك الحزمة وبدّل في بيئة التجربة فقط ملفات جذر المستودع `main.py`, `app.js`, `style.css`، دون تعديل Dockerfile أو نقل مسار الملفات.
3. راجع لقطات diff مع نسخة GitHub الأصلية المعتمدة قبل تطبيق أي تغيير.
4. انشر في staging؛ سيتم إنشاء جدولَي الاجتماعات عند بدء التطبيق عبر `Base.metadata.create_all`. ينصح بمراجعة هذا التغيير لاحقًا باستخدام ترحيلات قاعدة بيانات مرقّمة (Alembic) قبل الإنتاج.
5. جرّب إدارة الدعوات والصلاحيات أولًا، والفيديو لاحقًا بمزود LiveKit معتمد وبعد فحص الشبكة/الخصوصية.
6. لا ترفع هذه الحزمة مباشرة إلى `main` في المشروع الحالي ما لم تتأكد من نسخة احتياطية ونتائج قبول البيئة التجريبية.

## 6. حدود فنية يجب مراعاتها
- لم يتم إثبات أداء الفيديو في اتصال حي مع عميلَي متصفح، لأن بيئة الاختبار المتاحة لا تسمح بفتح المتصفح الآلي؛ الاختبارات المنفذة 12 اختبار API، و`node --check` و`py_compile`.
- اختبار WebRTC يتطلب فحص وصول العملاء إلى WSS والوسائط عبر UDP أو TURN/TLS، بحسب سياسة الشبكة، واعتماد النطاقات لدى الأمن السيبراني.
- خدمة الفيديو متخصصة خارج Railway (أو مستضافة ذاتيًا في بنية مستقلة)، ولذلك اشتراك Railway المدفوع **لا يغني** عن اشتراك أو استضافة مزود الوسائط.
- لا تتوفر حاليًا ميزات انتظار الموافقة لكل شخص في منتصف اتصال مباشر، أو التحكم في طرد مشارك قائم، أو تسجيل الاجتماع، أو نسخ المحضر إلى مهمة تلقائيًا؛ يمكن إضافتها في مرحلة لاحقة بعد اعتماد النموذج.
